# Карта клиентских экранов

Источники: `prototypes/booking-prototype/Booking Prototype.dc.html` (лендинг,
запись, подтверждение), `prototypes/booking-prototype/Client Account Prototype.dc.html`
(личный кабинет, профиль, уведомления, служебные страницы),
`prototypes/booking-prototype/Booking Flow Diagram.dc.html` (схема связи
экранов, лежит рядом с прототипом, не в `docs/`), код API в `server/src/routes/`.

**Важно до чтения таблицы:** оба прототипа — полностью статические макеты. Ни
один экран в них сейчас не вызывает реальный API (`fetch` встречается только
внутри служебного `support.js` самого инструмента прототипирования, к `/api/*`
обращений нет). Все данные захардкожены прямо в коде экрана. Колонки
«эндпоинты» ниже — это то, чем экран **должен** питаться при вёрстке, а не то,
чем он питается сейчас.

Из экранов, которые вы просили — лендинг, авторизация, запись, личный
кабинет, профиль, уведомления, служебные страницы — в прототипах теперь есть
**шесть из семи**: лендинг, запись, подтверждение, личный кабинет, профиль,
уведомления, служебные страницы. Не хватает только экрана **авторизации**
(вход/регистрация) — он по-прежнему нигде не сделан, подробности в разделе
ниже. Экраны мастера/администратора («Админка») в файле есть, но в карту не
включены — по вашей просьбе.

## Экраны

| Экран | Файл прототипа | Что видит клиент | Эндпоинты данных | Эндпоинты кнопок | Переходы |

| **Лендинг** | `Booking Prototype.dc.html` (блок `isLanding`) | Хедер с именем мастера и кнопкой «Записаться»; хиро-блок с заголовком и CTA; сетка карточек услуг (название, описание, длительность, цена); футер | `GET /api/services` — список услуг для карточек. Мастер захардкожен («Кабанов Олег»), в реальном API мастеров может быть несколько — `GET /api/masters` сейчас нигде не используется | Кнопка «Записаться» (хедер) и «Записаться на консультацию →» (хиро) — переход на экран «Запись», без вызова API. Кнопка «Записаться →» на карточке услуги — переход на «Запись» с предвыбранной услугой, без вызова API. Ссылка «Смотреть услуги» — якорный скролл, без API | → Запись (любая кнопка «Записаться»). → Админка через ссылку в футере (не в карте, экран мастера/админа) |
| **Запись** | `Booking Prototype.dc.html` (блок `isBooking`) | 4 шага одной формой: выбор услуги, выбор даты (сетка на 7 дней вперёд), выбор времени (фиксированный список слотов), поля контактов (имя, телефон/email, комментарий); сайдбар с резюме записи | Услуги — `GET /api/services`. Даты в прототипе сгенерированы на клиенте (просто «сегодня + 7 дней»), в реальности часть дат может быть недоступна (выходной мастера/блокировка) — эту информацию сейчас неоткуда взять на этапе выбора даты. Время в прототипе — фиксированный список `['10:00','11:30','13:00','14:30','16:00','17:30']` для любой даты; реальный источник свободного времени — `GET /api/masters/:masterId/availability?date=...&serviceIds=...`, который надо вызывать заново при каждой смене даты/услуги и который учитывает уже занятые слоты | Кнопка «Подтвердить запись» должна вызывать `POST /api/bookings` (масter Id, serviceIds, startsAt, опционально holdId, comment) — в прототипе она просто пишет объект в локальный state, реального вызова нет. Ссылка «← На главную» — переход, без API | → Лендинг («← На главную»). → Подтверждение (после «Подтвердить запись») |
| **Подтверждение** | `Booking Prototype.dc.html` (блок `isConfirmation`) | Галочка-иконка, номер записи, статус («ожидает подтверждения» и т.п.), карточка с деталями записи (услуга, дата, время, имя, контакт, статус) | Данные берутся из ответа `POST /api/bookings` (в проде) — отдельного GET для этого экрана не нужно, если открывать его сразу после успешного создания. Если экран может открываться по прямой ссылке/обновлению страницы — тогда нужен `GET /api/bookings/:id` | Кнопка «На главную» — переход на Лендинг, без API. Кнопка «Открыть панель администратора» — переход на Админку (не в карте) | → Лендинг. → Админка (не в карте) |
| **Личный кабинет** | `Client Account Prototype.dc.html` (блок `isCabinet`) | Список записей клиента с вкладками «Предстоящие / Прошедшие / Отменённые», карточка на каждую запись (услуга, дата, время, код, статус), у предстоящих — инлайн-переброс на новую дату/время и отмена; отдельное пустое состояние на каждую вкладку | `GET /api/bookings` — возвращает все записи клиента одним списком, без параметра фильтра по статусу/периоду. Деление на «предстоящие/прошедшие/отменённые» для вкладок нужно делать на клиенте (сравнивать `startsAt` с текущим временем и смотреть `status`) — эндпоинт для этого не нужен, но и не делает работу за фронтенд | «Новая запись» — переход на Лендинг/Запись, без API. | **Профиль** | `Client Account Prototype.dc.html` (блок `isProfile`) | Карточка с именем, email (нередактируемый, подписан «используется для входа») и контактом; кнопки «Редактировать» / «Сохранить» / «Отмена»; подтверждение «Изменения сохранены» | Прямого источника нет. Данные клиента в реальном приложении есть только в ответе `POST /api/auth/login` / `POST /api/auth/register` (`client: {id, name, email, contact}`) — их нужно держать в состоянии сессии на фронте, отдельного `GET /api/clients/me` в API нет | Кнопка «Сохранить» должна вызывать `PATCH /api/clients/me` — такого эндпоинта в API нет вообще (см. список ниже), поэтому в прототипе сохранение полностью локальное, ничего не персистится | ↔ Кабинет, ↔ Уведомления (общая навигация). → Лендинг («Выйти») |
| **Уведомления** | `Client Account Prototype.dc.html` (блок `isNotifications`) | Список уведомлений (точка-индикатор непрочитанного, заголовок, текст, время), бейдж с числом непрочитанных на вкладке в шапке, кнопка «Отметить всё прочитанным», переключатель «показать пустое состояние» для предпросмотра | Источника нет вообще — в API нет ни одного эндпоинта под уведомления клиента (ни списка, ни статуса прочтения). Весь список в прототипе — полностью придуманный мок | Клик по уведомлению и «Отметить всё прочитанным» должны вызывать эндпоинты пометки прочитанным — их не существует, сейчас всё меняется только в локальном state. | **Служебные страницы** | `Client Account Prototype.dc.html` (блок `isService`, 4 подсостояния через `serviceKind`) | Один экран с переключателем сверху («Загрузка» / «Пусто» / «404» / «Ошибка») — для предпросмотра всех четырёх состояний без открытия разных файлов: спиннер с текстом загрузки; пустое состояние с CTA «Записаться на консультацию»; 404 с CTA «На главную»; общая ошибка с «Обновить» и «На главную» | Эндпоинта у этого экрана как такового нет — это набор состояний, в которые попадает **любой** другой экран, пока его собственный запрос выполняется, вернул пустой список или упал с ошибкой. Переключатель вкладок вверху — инструмент для ревью прототипа, не часть реального UI | «Обновить» на состоянии «Ошибка» должен повторно вызывать тот запрос, который упал (в прототипе просто возвращает экран в состояние «Загрузка»). «На главную» — переход на Лендинг, без API | Не самостоятельный переход — экран подставляется вместо любого другого, пока у него нет данных или что-то пошло не так |

## Что из списка экранов всё ещё отсутствует

- **Авторизация (вход/регистрация).** Ни в одном из двух прототипов формы логина/регистрации нет — форма записи на шаге «Контакты» просто спрашивает имя и телефон/email без создания аккаунта, а личный кабинет/профиль/уведомления открываются сразу, без экрана входа перед ними. Но реальный API требует авторизованного клиента (`Authorization: Bearer <token>`) для создания записи, просмотра, переноса, отмены и для всего личного кабинета — `POST /api/auth/register`, `POST /api/auth/login`, `POST /api/auth/logout` готовы и по-прежнему ничем не покрыты.

## Экраны, для которых в API не хватает данных

- **Запись, шаг «Дата».** Нужен список дат с пометкой, какие вообще доступны у мастера (рабочие дни минус блокировки), до того как клиент выберет конкретную дату и запросит `availability`. Сейчас такого «эндпоинта на месяц/неделю вперёд» нет — есть только `availability` на одну конкретную дату.
- **Запись, шаг «Время».** Если делать честно (как задумано в API) — при смене даты нужно каждый раз дёргать `GET /api/masters/:masterId/availability`, но сама эта функция не выбирает мастера заранее нигде на экране «Запись» — мастер в прототипе не выбирается вообще (захардкожен один), а `masterId` обязателен для availability, для hold и для создания записи. Нужен либо явный шаг выбора мастера, либо решение «мастер один — зашить его id в конфиг фронтенда».
- **Личный кабинет.** `GET /api/bookings` достаточно для самого списка, но не хватит для отображения статуса удержания слота (`slot_holds`), если планируете показывать клиенту его текущие незавершённые «черновики» записи — под это нет отдельного клиентского эндпоинта.
- **Профиль.** Не хватает вообще всего эндпоинта — ни получить, ни сохранить данные профиля сейчас нечем (см. список ниже). Экран в прототипе работает полностью на локальных моковых данных.
- **Уведомления.** Не хватает всего — ни списка, ни статуса прочтения. Весь экран сейчас чистый мок без какой-либо связи с API.

## Эндпоинты, которым не нашлось экрана

- `POST /api/auth/register`, `POST /api/auth/login`, `POST /api/auth/logout` — по-прежнему нет экрана авторизации.
- `POST /api/holds`, `DELETE /api/holds/:id` — временное удержание слота на время заполнения формы (10 минут, см. `HOLD_TTL_MINUTES` в конфиге сервера); ни в экране «Запись», ни в «Личном кабинете» слот ничем не удерживается между выбором времени и подтверждением, из-за чего его теоретически может перехватить другой клиент, пока первый дозаполняет форму.
- `GET /api/masters` — публичный список мастеров; нигде не используется, потому что мастер везде захардкожен как единственный.

## Эндпоинты, которых не хватает в API (нужны под уже готовые экраны)

- `GET /api/clients/me`, `PATCH /api/clients/me` — под экран «Профиль»: получить и сохранить данные текущего клиента. Сейчас данные клиента отдаются только один раз, внутри ответа логина/регистрации.
- Любой эндпоинт под уведомления клиента (список + отметка прочитанным) — под экран «Уведомления». Сейчас в API таблицы/логики уведомлений нет вовсе, это отдельная фича с нуля, включая бэкенд.
