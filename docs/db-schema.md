# Схема базы данных (SQLite) — Booking Prototype

Документ описывает схему БД для прототипа записи на консультацию
(`prototypes/booking-prototype/Booking Prototype.dc.html`). Экраны прототипа:
**Лендинг → Запись → Подтверждение → Админка** (см. `Booking Flow Diagram.dc.html`).

Это документ проектирования, без реализации: SQL в разделе 8 приведён как
формальная запись схемы, а не как код приложения.

## 1. Область охвата и допущения

> **Обновление после первой версии документа.** Изначально здесь было
> зафиксировано решение не заводить отдельную таблицу `masters` (один
> специалист на весь бизнес) и не давать клиентам аккаунтов. При сборке
> API поверх этой схемы оба допущения снял сам заказчик — понадобились
> «список мастеров»/«управление мастерами» и полноценные «регистрация,
> вход, выход» для клиентов. Ниже — уже актуальное описание с `masters`
> и аккаунтами клиентов; исходные формулировки лежат в истории git и в
> `docs/db-notes.md` (журнал изменений), если нужно вспомнить, почему
> было так, как было.

- Бизнес может иметь несколько мастеров (`masters`); график работы и
  блокировки времени привязаны к конкретному мастеру, не общие на всю
  систему.
- Клиенты — полноценные аккаунты с email и хешем пароля, а не только
  «имя+контакт», введённые разово при записи (как было в исходном
  прототипе `prototypes/booking-prototype/`). Экрана регистрации/входа в
  самом DC-прототипе нет — это уже развитие продукта поверх него.
- Прототип не содержит экрана логина в админку, но пароль явно должен
  где-то храниться в виде хеша (требование 5) — значит, для реальной
  системы нужна таблица администраторов. Она добавлена как минимально
  необходимая для защиты `/admin`, даже если в прототипе экрана входа нет.
- Оплата в прототипе не производится (нет экрана оплаты/чека) — таблиц для
  платежей нет.

## 2. Экраны и данные

| Экран | Что показывает | Источник данных |
|---|---|---|
| **Лендинг** | Название специалиста (статический контент, не в БД), карточки услуг: название, описание, длительность, цена | `services` |
| **Запись — Шаг 1 (Услуга)** | Список услуг для выбора | `services` |
| **Запись — Шаг 2 (Дата)** | Ближайшие дни, часть из них недоступна (выходной/полностью занято) | `work_schedule` + `bookings` + `schedule_blocks` (вычисляется на лету) |
| **Запись — Шаг 3 (Время)** | Свободные слоты на выбранную дату | то же вычисление, с учётом `services.duration_minutes` |
| **Запись — Шаг 4 (Контакты)** | Поля «Имя», «Контакт», «Комментарий» | вводятся пользователем → `clients`, `bookings.comment` |
| **Запись — сводка/сабмит** | Выбранные услуга/дата/время; по кнопке «Подтвердить запись» создаётся запись | новая строка в `bookings` (+ новая или существующая строка в `clients`) |
| **Подтверждение** | Номер записи, услуга, дата, время, имя, контакт, статус («Ожидает подтверждения») | `bookings` JOIN `clients`, `services` |
| **Админка — счётчики** | Всего / ожидают / подтверждено | `COUNT(*)` по `bookings.status` |
| **Админка — список записей** | Имя и контакт клиента, услуга, дата+время, статус, кнопки «Подтвердить»/«Отменить» | `bookings` JOIN `clients`, `services`; кнопки меняют `bookings.status` |

## 3. Список таблиц

### 4.4 `sessions` — Сессии (клиенты, администраторы, мастера)

| Поле | Тип | Обязательное | Ключ | Описание |
|---|---|---|---|---|
| `id` | INTEGER | да | PK, AUTOINCREMENT | Суррогатный ключ |
| `token` | TEXT | да | UNIQUE | Значение из заголовка `Authorization: Bearer <token>` |
| `actor_type` | TEXT | да | CHECK IN (`client`,`admin`,`master`) | Кто владелец сессии |
| `actor_id` | INTEGER | да | — (см. ниже) | id из `clients`, `admin_users` или `masters`, в зависимости от `actor_type` |
| `created_at` | TEXT | да | — | ISO-8601 |
| `expires_at` | TEXT | да | — | ISO-8601; после этого момента сессия недействительна |

У `actor_id` намеренно нет `FOREIGN KEY` — он указывает то в `clients`, то
в `admin_users`, то в `masters` в зависимости от `actor_type` (полиморфная
ссылка), а SQLite не умеет условные внешние ключи. Целостность здесь
поддерживает код (`src/sessions.js`, `src/authz.js`), а не сама схема.

`master` в списке значений `actor_type` появился миграцией
`0005_master_login.sql` — CHECK-ограничение с фиксированным списком
значений SQLite не даёт изменить через `ALTER TABLE`, только пересоздать
таблицу (переименовать, создать заново с новым CHECK, скопировать
данные, удалить старую — стандартная процедура из документации SQLite
для того, что `ALTER TABLE` не поддерживает напрямую). `AUTOINCREMENT`
при этом не сбрасывается: явная вставка существующих `id` в таблицу с
`INTEGER PRIMARY KEY AUTOINCREMENT` обновляет `sqlite_sequence` так же,
как обычная вставка — проверено отдельно перед тем, как полагаться на
это в миграции.

## 5. Формат дат и времени

Единый формат — **ISO-8601, TEXT, в UTC**:

- Дата+время (моменты): `YYYY-MM-DDTHH:MM:SSZ`, например `2026-09-12T11:30:00Z`.
  Используется в `starts_at`/`ends_at`/`created_at`/`updated_at`/`last_login_at`.
- Только время суток (правило графика, без даты): `HH:MM`, 24-часовой формат,
  например `10:00`. Используется в `work_schedule.start_time`/`end_time`.

Почему так:

1. У SQLite нет отдельного типа «дата/время» — есть только
   NULL/INTEGER/REAL/TEXT/BLOB, и сама документация SQLite рекомендует
   хранить даты как TEXT в ISO-8601 либо как INTEGER Unix-время. TEXT
   выбран как более читаемый при отладке и просмотре данных напрямую.
2. Строки в этом формате сравниваются и сортируются как обычный текст
   (`ORDER BY starts_at`, `WHERE starts_at > ...`) и дают тот же порядок,
   что и по времени — не нужны кастомные функции сравнения.
3. Формат напрямую работает со встроенными функциями SQLite
   (`date()`, `datetime()`, `strftime()`), которые нужны для расчёта
   пересечений интервалов при вычислении свободных слотов.
4. Хранение в UTC убирает неоднозначность перевода часов (переход на
   зимнее/летнее время). Конвертация в локальное время специалиста —
   задача уровня приложения, а не БД. `work_schedule` хранит именно
   часы работы «по местному времени бизнеса» (без даты, поэтому
   привязки к UTC не требует), и приложение переводит `HH:MM` конкретного
   дня в UTC при сравнении с `bookings`/`schedule_blocks`.

## 6. Вычисление свободных слотов (без готовой таблицы)

Свободное время мастера *K* на дату *D* для набора выбранных услуг с
суммарной длительностью *M* минут (`M = Σ services.duration_minutes` по
всем выбранным услугам) получается на лету:

1. Взять `work_schedule` мастера *K* по дню недели даты *D* → если строки
   нет или `is_working = 0`, свободных слотов нет; иначе получить
   `start_time`/`end_time` этого дня (местное время салона) и перевести их
   в UTC (`salonLocalToUtcIso`, см. раздел 5).
2. Подчистить просроченные `slot_holds` (`expires_at <= now`) — лениво,
   прямо перед расчётом (плюс отдельная периодическая подчистка в
   `server/src/index.js`, см. `docs/db-notes.md`).
3. Разбить интервал `[start_time, end_time)` даты *D* на потенциальные
   слоты с шагом *M* минут.
4. Убрать из потенциальных слотов те, что пересекаются с существующими
   записями этого мастера (`bookings`, где `status <> 'cancelled'`) — эти
   интервалы уже заняты клиентами.
5. Убрать слоты, пересекающиеся с `schedule_blocks` этого мастера — это
   недоступность самого мастера, а не чья-то запись.
6. Убрать слоты, пересекающиеся с ещё не истёкшими `slot_holds` этого
   мастера — эти интервалы прямо сейчас оформляет другой клиент.
7. Оставшиеся слоты — то, что возвращает
   `GET /api/masters/:masterId/availability`. Отменённые записи
   (`status = 'cancelled'`) и истёкшие удержания не блокируют время — оно
   снова становится доступным.

Ничего из этого не материализуется в отдельную таблицу — источники
правды всегда `work_schedule`, `bookings`, `schedule_blocks` и
`slot_holds` (требование 3). Реализация — `server/src/availability.js`.

## 6a. Защита от пересечения записей — три независимых уровня

Одной проверки в коде приложения недостаточно (гонка между «проверили —
свободно» и «записали» при двух почти одновременных запросах), поэтому
защита продублирована на трёх уровнях, каждый из которых ловит то, что
может проскочить мимо предыдущего:

1. **Приложение, до похода в БД** — `assertSlotIsFree()` в
   `server/src/availability.js`, вызывается из `createBooking()` и
   `rescheduleBooking()` (`server/src/bookings.js`). Даёт понятную ошибку
   и список подсказок ещё до того, как транзакция вообще началась —
   самый частый путь в нормальной работе, без гонок.
2. **Блокировка на уровне транзакции** — `BEGIN IMMEDIATE` вместо обычного
   `BEGIN` в `createBooking()`/`rescheduleBooking()` (подробности и
   почему — раздел 6b). Делает «проверить и записать» одной неделимой
   операцией для конкурентных запросов, а не только последовательным
   кодом внутри одного вызова.
3. **Триггеры в самой БД** — `trg_bookings_no_overlap_insert` и
   `trg_bookings_no_overlap_update` (`0003_no_overlap_triggers.sql`).
   Последний рубеж: сработает, даже если приложенческую проверку кто-то
   обошёл, отключил или обновление таблицы пришло не из
   `server/src/bookings.js`, а из миграции, скрипта или ручного фикса
   данных. Условие — ровно по постановке: `NEW.starts_at < b.ends_at AND
   NEW.ends_at > b.starts_at` (визиты впритык, `15:00–16:00` и
   `16:00–17:00`, пересечением не считаются — сравнение строгое); не
   реагирует, если сама запись отменена (`WHEN NEW.status <>
   'cancelled'`) или если другая запись уже отменена. Один триггер на
   `INSERT` и отдельный на `UPDATE` — потому что и перенос времени, и
   смена мастера меняют строку через `UPDATE`, а не создают новую, и оба
   обязаны пройти ту же проверку. Ошибка использует фиксированный текст
   (`RAISE(ABORT, 'booking_overlap')`), по которому API отличает именно
   этот конфликт от прочих ошибок и не показывает пользователю сырой
   текст SQLite (раздел 6c).

Частичный уникальный индекс `ux_bookings_master_active_start` (раздел 7)
остаётся дополнительной подстраховкой на самый частый частный случай
(точное совпадение времени начала) — он дешевле в проверке, чем триггер,
и продолжает работать, даже если триггеры когда-нибудь по ошибке удалят
из миграций.

### Осознанное наложение администратором

`bookings.override_overlap` (миграция `0004_admin_overlap_override.sql`)
— управляемый обход всех трёх уровней выше, но только «в одну сторону»:

- Оба триггера получили `AND NEW.override_overlap = 0` в `WHEN` — то есть
  пропускают проверку, только если флаг стоит у **вставляемой/обновляемой**
  строки. Сам `EXISTS(...)` внутри триггера по-прежнему учитывает вообще
  все активные записи мастера, независимо от их `override_overlap` — это
  и даёт «в одну сторону»: помеченная запись может лечь поверх занятого
  времени, но не открывает это время для всех остальных.
- Частичный уникальный индекс получил то же условие
  (`WHERE status <> 'cancelled' AND override_overlap = 0`), иначе точное
  совпадение `starts_at` с уже существующей записью упёрлось бы в
  `UNIQUE` ещё до триггера.
- В приложении флаг может стать `true` только внутри
  `adminCreateBooking()` (`server/src/bookings.js`), которая вызывается
  из **одного-единственного** маршрута — `POST /api/admin/bookings`
  (`server/src/routes/admin.routes.js`), сразу за `requireAdmin(req)`.
  Клиентский `createBooking()` (маршрут `POST /api/bookings`) жёстко
  передаёт `overrideOverlap: false` в общее ядро `createBookingCore()` —
  маршрут даже не читает это поле из тела запроса, так что прислать его
  клиенту физически нечем: см. раздел «Роль и запрос клиента» ниже.
- `assertSlotIsFree()` получила параметр `allowBookingOverlap` — снимает
  ровно проверку «уже есть активная запись на это время», но не рабочие
  часы мастера, не его блокировки (`schedule_blocks`) и не чужие
  удержания слота (`slot_holds`). «Поверх занятого времени» в задаче
  означает конфликт с другой записью, а не разрешение работать вне
  графика или поверх отпуска — это разные, не связанные с двойной
  записью ограничения, и обходить их заодно никто не просил.
- `rescheduleBooking()` при переносе всегда сбрасывает
  `override_overlap` обратно в `0` (`UPDATE ... SET ..., override_overlap
  = 0, ...`), даже если запись раньше была создана с наложением: старое
  наложение было решением для старого времени, а не бессрочным пропуском
  проверки для этой записи. Требование «дальше участвует в проверке
  пересечений как обычная» относится и к самой этой записи при
  последующих изменениях её времени, не только к тому, как её видят
  другие. `adminSetBookingStatus()` (подтверждение/отмена) флаг не
  трогает — она не меняет время записи, пересматривать нечего.

#### Роль и запрос клиента

Проверка роли — `requireAdmin(req)` в начале обработчика
`POST /api/admin/bookings` (`server/src/routes/admin.routes.js`), которая
делегирует в `requireActor(req, "admin")` (`server/src/authz.js`): нет
валидной сессии — `401`; сессия валидна, но принадлежит клиенту — `403`.

Если клиент (или кто угодно без админской сессии) отправит
`overrideOverlap: true` в `POST /api/bookings` — тела запросов в этом
пути обрабатывает `routes/bookings.routes.js`, которая явно перечисляет,
какие поля читает из тела (`masterId`, `serviceIds`, `startsAt`, `holdId`,
`comment`), и `overrideOverlap` среди них нет — значение просто никогда
не читается и никуда не попадает. Даже если бы кто-то по ошибке
протащил его дальше, `createBooking()` вызывает общее ядро с буквально
прописанным `overrideOverlap: false`, не значением из аргументов —
переопределить это без изменения кода невозможно. Итог для клиента: сам
факт присутствия поля в JSON ни на что не влияет, конфликт по времени
проверяется и блокируется как обычно, `overrideOverlap:true` в теле
клиентского запроса эквивалентно его отсутствию.

## 6b. `BEGIN IMMEDIATE`, а не обычный `BEGIN`

`createBooking()` и `rescheduleBooking()` открывают транзакцию командой
`BEGIN IMMEDIATE`, а не `BEGIN` (= `BEGIN DEFERRED`, поведение по
умолчанию). Разница: `BEGIN DEFERRED` не берёт вообще никакой блокировки
в момент старта — блокировка на запись (`RESERVED`) появляется только
когда транзакция доходит до первой реальной `INSERT`/`UPDATE`/`DELETE`.
Это значит, что между «прочитали и решили, что слот свободен» и «начали
записывать» есть окно, в которое может вклиниться второй писатель —
именно та гонка, которую нужно закрыть. `BEGIN IMMEDIATE` берёт
`RESERVED`-блокировку сразу на `BEGIN`, до какого-либо чтения — поэтому
второй `BEGIN IMMEDIATE` от другого соединения (второй HTTP-запрос,
другой процесс) будет ждать (или получит `SQLITE_BUSY`, если время
ожидания вышло) до тех пор, пока первая транзакция не завершится
`COMMIT`/`ROLLBACK`. Проверка занятости и сама запись становятся одной
неделимой операцией не только внутри одного вызова JS, но и между
конкурентными запросами — проверено вживую тремя одновременными `POST
/api/bookings` на один слот: ровно один получил `201`, два других —
чистый `409` (см. `docs/db-notes.md`).

`BEGIN EXCLUSIVE` не нужен — он блокирует ещё и параллельные *чтения*,
а нам достаточно исключить только параллельную запись; `GET
/api/masters/:id/availability` в это время должен продолжать читать
последнюю зафиксированную версию данных.

## 6c. Обработка конфликта в API

Обе ошибки — от частичного уникального индекса и от триггера —
перехватываются в одном месте (`isBookingOverlapError()` в
`server/src/bookings.js`) и превращаются в одинаковый ответ:
`slotTakenError()` (`server/src/availability.js`) отдаёт `409` с кодом
`slot_taken`, заранее заданным текстом на русском и списком из нескольких
ближайших свободных слотов этого мастера (`findNearestFreeSlots()` —
считается на лету тем же алгоритмом, что и обычная доступность, начиная
с запрошенного времени). Сырой текст ошибки SQLite (`error.message`) в
ответ клиенту никогда не попадает — он используется только внутри
`isBookingOverlapError()` для распознавания, что это именно конфликт
слота, а не что-то другое.

## 7. Уникальные ограничения и индексы

| Ограничение / индекс | Простыми словами | Что сломается без него |
|---|---|---|
| `UNIQUE(bookings.code)` | Номер записи, который видит клиент, должен быть один на каждую запись | Два клиента могли бы получить один и тот же номер BK-хххх — открыв «свою» запись, увидели бы чужую |
| Частичный `UNIQUE(bookings.master_id, starts_at) WHERE status <> 'cancelled' AND override_overlap = 0` | У одного мастера на одно и то же время не может быть двух активных обычных записей | Двойной клик по «Подтвердить запись» или гонка запросов создали бы два клиента на один и тот же слот одного мастера — он физически не сможет принять обоих. Ограничение по паре с `master_id`, а не по одному `starts_at`, — иначе два *разных* мастера не могли бы принимать в одно и то же время. Раньше это была единственная защита от точного совпадения времени начала, а частичные пересечения интервалов разной длины (например, `10:00–11:00` и `10:30–11:30`) вообще ничем на уровне схемы не ловились — теперь это закрывают триггеры из раздела 6a, а индекс остался как дешёвая дополнительная подстраховка. `AND override_overlap = 0` в условии индекса добавлен вместе с наложением от администратора — иначе точное совпадение времени с уже существующей записью упёрлось бы в этот `UNIQUE` ещё до триггера, который как раз обязан такое пропустить |
| Индекс `bookings(status)` | Ускоряет подсчёт «всего/ожидают/подтверждено» в админке | При росте числа записей подсчёт статусов станет полным сканированием таблицы на каждое открытие админки |
| Индекс `bookings(master_id, starts_at)` | Ускоряет поиск записей конкретного мастера на дату/диапазон при расчёте свободных слотов | Каждый расчёт доступного времени сканировал бы записи всех мастеров, а не только нужного |
| Индекс `bookings(client_id)` | Ускоряет поиск истории записей конкретного клиента | SQLite не индексирует внешние ключи автоматически — без индекса это полное сканирование таблицы |
| `UNIQUE(services.name)` | В каталоге не может быть двух услуг с одинаковым названием | Админ мог бы случайно завести дубликат — на лендинге появятся две одинаковые карточки, а статистика по «услуге» размажется между двумя id |
| `UNIQUE(work_schedule.master_id, weekday)` | На каждый день недели у каждого мастера — ровно одно правило графика | Два конфликтующих правила на один день одного мастера сделают расчёт свободных слотов недетерминированным |
| `UNIQUE(admin_users.username)` | Логин однозначно определяет одну учётную запись | При входе или сбросе пароля было бы неясно, какую из нескольких учёток с одинаковым логином использовать |
| `UNIQUE(clients.email)` | Email клиента — уникальный логин | Регистрация второго аккаунта с тем же email сделала бы вход неоднозначным — непонятно, в какой аккаунт пускать |
| `UNIQUE(masters.email)` | Email мастера (если вход ему включён) — тоже уникальный логин | Тот же риск, что и с `clients.email`: два мастера с одним email — неясно, в чью учётку пускать при входе |
| `UNIQUE(sessions.token)` | Токен сессии однозначно определяет, кто сделал запрос | Коллизия токенов пустила бы одного пользователя под чужой сессией |
| Индекс `sessions(actor_type, actor_id)` | Быстро найти/отозвать все сессии конкретного клиента или админа | Логаут «везде» или проверка активных сессий сканировали бы всю таблицу |
| Индекс `sessions(expires_at)` | Ускоряет периодическую подчистку истёкших сессий | Фоновая очистка (`server/src/index.js`) сканировала бы все сессии, а не только просроченные |
| Индекс `schedule_blocks(master_id, starts_at, ends_at)` | Ускоряет поиск блокировок конкретного мастера, пересекающих нужный день | Расчёт свободных слотов сканировал бы блокировки всех мастеров за всё время |
| Индекс `slot_holds(master_id, starts_at, ends_at)` | Ускоряет поиск активных удержаний конкретного мастера на нужный диапазон | Расчёт слотов и создание нового удержания сканировали бы все удержания всех мастеров |
| Индекс `slot_holds(expires_at)` | Ускоряет подчистку истёкших удержаний | Автоматическое «освобождение» слота после истечения удержания (требование 4) стало бы полным сканированием на каждую подчистку |
| Индекс `clients(contact)` | Ускоряет поиск клиента/его записей по телефону или email | Поиск «у нас уже был этот человек» станет полным сканированием таблицы клиентов |

`booking_services` и `slot_hold_services` используют составной
`PRIMARY KEY (booking_id, service_id)` / `(hold_id, service_id)` — это
одновременно и уникальность («одна и та же услуга не может быть добавлена
в одну запись/удержание дважды»), и готовый индекс для быстрого поиска
услуг по записи/удержанию.

## 8. Приложение: DDL (справочно)

Ниже — итоговая схема (эквивалент `0001_init.sql` +

Фактические файлы миграций в `server/src/migrations/` устроены иначе —
второй файл дополняет первый через `ALTER TABLE`, а не переписывает его

```sql
CREATE UNIQUE INDEX ux_masters_email ON masters(email);

  ends_at     TEXT NOT NULL,

-- См. раздел 6a. Один триггер на INSERT, отдельный на UPDATE — перенос
-- записи и смена мастера идут через UPDATE, не через новую вставку.
-- override_overlap = 1 у ВСТАВЛЯЕМОЙ/ОБНОВЛЯЕМОЙ строки пропускает
-- проверку для неё самой (осознанное наложение администратором), но не
-- влияет на EXISTS(...) — другие записи по-прежнему не могут пересекаться
-- с ней, override_overlap других строк здесь ни при чём.
CREATE TRIGGER trg_bookings_no_overlap_insert
BEFORE INSERT ON bookings
WHEN NEW.status <> 'cancelled' AND NEW.override_overlap = 0
BEGIN
  SELECT RAISE(ABORT, 'booking_overlap')
  WHERE EXISTS (
    SELECT 1 FROM bookings b
    WHERE b.master_id = NEW.master_id
      AND b.status <> 'cancelled'
      AND NEW.starts_at < b.ends_at
      AND NEW.ends_at > b.starts_at
  );
END;

CREATE TRIGGER trg_bookings_no_overlap_update
BEFORE UPDATE ON bookings
WHEN NEW.status <> 'cancelled' AND NEW.override_overlap = 0
BEGIN
  SELECT RAISE(ABORT, 'booking_overlap')
  WHERE EXISTS (
    SELECT 1 FROM bookings b
    WHERE b.master_id = NEW.master_id
      AND b.status <> 'cancelled'
      AND b.id <> NEW.id
      AND NEW.starts_at < b.ends_at
      AND NEW.ends_at > b.starts_at
  );
END;
```

## 9. Спорные решения

1. ~~Нет таблицы `masters`.~~ **Устарело.** Так было в первой версии
   схемы (один специалist, глобальный график). При сборке API это решение
   явно отменили: добавлена таблица `masters`, `work_schedule`/
   `schedule_blocks`/`bookings` получили `master_id`. Оставляю пункт как
   след истории — см. `docs/db-notes.md`, почему передумали.

2. **`clients.contact` — одно свободное текстовое поле, без уникальности.**
   В форме записи одно поле «Телефон или email» — схема повторяет это
   один в один. Осознанно не делаю его уникальным: один и тот же человек
   может ввести номер в разных форматах («+7 999...» и «8999...») и
   уникальность по строке создала бы ложные ограничения, а настоящая
   дедупликация клиентов требует нормализации телефона/email, чего нет
   в прототипе. Плата за это — один и тот же человек может попасть в
   `clients` несколькими строками.

3. **Статусы — `CHECK`, а не отдельная таблица-справочник.** В прототипе
   статусов ровно три (`pending`/`confirmed`/`cancelled`), заданы в коде
   константой `STATUS_META`, и в UI нет способа завести новый статус.
   `CHECK`-ограничение проще и достаточно строгое (требование 4); отдельная
   таблица `booking_statuses` была бы более гибкой для будущего расширения
   набора статусов, но для текущего прототипа — лишняя сущность.

4. **Защита от двойной записи — только по точному совпадению времени
   начала.** Частичный уникальный индекс на `starts_at` ловит самый частый
   случай (повторный клик/гонка запросов на один и тот же слот), но не
   ловит частично пересекающиеся интервалы разной длины (например, запись
   на 60 минут с 10:00 и запись на 30 минут с 10:30). SQLite не
   поддерживает ограничения на пересечение интервалов на уровне схемы
   (в отличие от `EXCLUDE` в PostgreSQL) — полная защита от пересечений
   должна проверяться в коде приложения перед вставкой, используя тот же
   алгоритм, что вычисляет свободные слоты (раздел 6).

5. **Цена — `INTEGER` в копейках, а не `REAL` в рублях.** Деньги в виде
   `REAL` подвержены ошибкам двоичного округления (классический пример:
   0.1 + 0.2 ≠ 0.3). Целые копейки считаются точно; цена ₽ получается
   делением на 100 на уровне приложения при отображении.

6. **`bookings.ends_at` хранится явно, а не вычисляется join’ом с
   `services.duration_minutes` на каждый запрос.** Это небольшая
   денормализация, но она даёт две вещи: быстрый поиск пересечений при
   расчёте слотов без join, и защиту истории — если позже изменить
   длительность услуги в `services`, уже созданные записи не «поедут» по
   времени задним числом.

7. **Все моменты времени — в UTC, `work_schedule` — в местном времени
   бизнеса без часового пояса.** Это стандартный подход, устраняющий
   баги перехода на летнее/зимнее время при хранении `starts_at`/`ends_at`.
   Плата — схема неявно предполагает один часовой пояс для всего бизнеса;
   поддержка клиентов из разных часовых поясов потребовала бы хранить
   часовой пояс явно.

8. **Добавлены `services.sort_order` и `admin_users`, которых нет в явном
   виде на экранах прототипа.** `sort_order` — потому что реальный админ
   почти наверняка захочет управлять порядком карточек на лендинге, а не
   зависеть от порядка вставки строк. `admin_users` — потому что
   требование 5 (поле для хеша пароля) осмысленно только при наличии
   таблицы учётных записей, хотя экрана логина в прототипе нет.

9. **`clients.email`/`password_hash` и `bookings.master_id` — nullable на
   уровне колонки.** По-хорошему это должно быть `NOT NULL`: у любого
   реального клиента теперь есть аккаунт, у любой новой записи — мастер.
   Но обе колонки добавлены `ALTER TABLE ... ADD COLUMN` поверх таблиц,
   где уже были строки без этих данных (демо-клиенты изначального
   прототипа, записи без понятия «мастер»). SQLite не даёт задним числом
   поставить `NOT NULL` на непустую таблицу без значения по умолчанию, а
   подставлять фиктивное значение ради формальной строгости схемы не
   стал — это спрятало бы реальные пропуски данных за фальшивым «not
   null». Обязательность обеспечивает код (`src/validation.js`,
   `src/bookings.js`) на границе API. Подробности — `docs/db-notes.md`.

10. **Одна запись/удержание — несколько услуг через `booking_services`/
    `slot_hold_services`, а не одна колонка `service_id`.** Изначально в
    `bookings` был единственный `service_id`. Когда понадобилось
    «удержание слота... с учётом суммарной длительности выбранных услуг»,
    стало ясно, что одна запись должна уметь включать несколько услуг
    сразу (например, консультацию и разбор прототипа одним визитом).
    Связывающая таблица — стандартный способ выразить «многие ко многим»
    без денормализации в духе `service_ids TEXT` со списком id в строке
    (такое поле нельзя было бы ни проиндексировать, ни защитить `FOREIGN
    KEY`).

11. **`slot_holds` — отдельная таблица, а не запись во «временном»
    статусе внутри `bookings`.** Можно было бы заводить `bookings` сразу
    со статусом вроде `held` и чистить их по таймауту. Не стал: у
    удержания принципиально другой жизненный цикл (живёт минуты, не
    видно клиенту как «моя запись», не должно попадать в списки/историю
    записей) и другие поля (`expires_at`, которого у записи нет). Хранить
    их вместе означало бы либо постоянно фильтровать `bookings` по статусу
    везде, где выводятся реальные записи, либо держать в одной таблице
    сущности с разным смыслом. Отдельная таблица + отдельная
    `slot_hold_services` — чище, а частичный `UNIQUE`-индекс на
    `bookings` при этом продолжает защищать только настоящие записи.

12. **`sessions` — одна таблица на клиентов и админов, без `FOREIGN KEY`
    на `actor_id`.** Мог быть `client_sessions` + `admin_sessions`
    отдельно (тогда `actor_id` можно было бы связать `FOREIGN KEY`) или
    JWT вместо серверных сессий вовсе. Общая таблица выбрана, потому что
    логика входа/выхода/проверки токена у обеих ролей идентична, а
    JWT — нет, потому что «выход» должен реально аннулировать доступ
    (у JWT без чёрного списка это невозможно, а список токенов —
    это, по сути, та же таблица `sessions`). Плата — `actor_id` не
    защищён `FOREIGN KEY` на уровне схемы (SQLite не умеет условные
    внешние ключи «то на одну таблицу, то на другую»); ссылочную
    целостность здесь поддерживает только код (`src/sessions.js`,
    `src/authz.js`), а не сама база.

13. **Часовой пояс салона — константа в `.env`
    (`SALON_UTC_OFFSET_MINUTES`), а не колонка в БД.** Раздел 9 (было)
    уже фиксировал допущение об одном часовом поясе на весь бизнес — оно
    не изменилось с приходом нескольких мастеров: все мастера одного
    бизнеса по-прежнему работают в одном городе/поясе. Если это когда-то
    перестанет быть так (мастера в разных часовых поясах), пояс нужно
    будет перенести в `masters.timezone_offset_minutes` — это добавление
    колонки, не переработка схемы.

14. **Триггеры проверяют пересечение полным сканированием активных
    записей мастера, а не только соседей по времени.** `EXISTS (SELECT 1
    FROM bookings b WHERE b.master_id = ... AND b.status <> 'cancelled'
    AND ...)` не ограничен диапазоном заранее — полагается на то, что
    индекс `ix_bookings_master_starts_at (master_id, starts_at)` сделает
    выборку по `master_id` дешёвой, а дальше SQLite сам отсеет
    непересекающиеся строки по `starts_at`/`ends_at` без полного
    сканирования всей таблицы. Отдельный индекс именно под условие
    пересечения (по `ends_at`) не заводил: записей на одного мастера
    даже при активном использовании — сотни-тысячи, не миллионы, а
    целиться в такую оптимизацию заранее, не увидев реальной нагрузки, —
    преждевременно.

15. **Ошибку конфликта отличаем по тексту `RAISE(ABORT, 'booking_overlap')`,
    а не по коду ошибки SQLite.** `node:sqlite` отдаёт для любого
    `RAISE(ABORT, ...)` один и тот же обобщённый `code: 'ERR_SQLITE_ERROR'`
    и числовой `errcode` (constraint-класс), не расшифровывая, какое
    именно ограничение сработало — различать пришлось бы по `errcode`
    вручную сверяясь с таблицей кодов SQLite, что более хрупко (детали
    может поменять апгрейд версии SQLite/Node), чем сравнить
    `error.message` со строкой, которую сами же и задали в тексте
    `RAISE`. Плата — если когда-нибудь понадобится второй триггер с
    другим смыслом ошибки на этой же таблице, тексты RAISE обязаны быть
    разными, иначе `isBookingOverlapError()` перепутает их.

16. **`BEGIN IMMEDIATE`, а не `BEGIN EXCLUSIVE`.** `EXCLUSIVE` блокирует
    ещё и параллельные чтения (в режиме без WAL это фактически то же
    самое, что `IMMEDIATE`, но семантически рассчитан на полный запрет
    любого другого доступа) — избыточно: `GET
    /api/masters/:id/availability` должен спокойно продолжать читать,
    пока идёт оформление чужой записи; важно исключить только
    одновременную запись, а не чтение.

17. **Наложение (`override_overlap`) снимает только проверку «занято
    другой записью», а не рабочие часы/блокировки/удержания.** В задаче
    было буквально «создавать запись поверх занятого времени» — это про
    конфликт с другой записью. Расширять обход на `outside_working_hours`,
    `slot_blocked` (блокировки мастера) или `slot_held` (чужое удержание)
    никто не просил, и это разные по смыслу ограничения: занятое время —
    про две записи, претендующие на одного мастера, а рабочие часы и
    блокировки — про доступность самого мастера в принципе. Если позже
    понадобится и это обходить, разумнее заводить отдельный флаг с другим
    именем, а не расширять смысл `override_overlap` задним числом.

18. **`override_overlap` сбрасывается в `0` при переносе записи, но не
    при смене статуса.** Перенос меняет время — если оставить флаг как
    есть, запись после переноса на новое (уже свободное на вид) время
    навсегда сохранила бы иммунитет к проверке пересечений, что явно
    противоречит «дальше участвует в проверке пересечений как обычная».
    Смена статуса (`adminSetBookingStatus`) время не трогает — сбрасывать
    там нечего, а сброс без причины дал бы неожиданный `409` при простом
    подтверждении/отмене записи, если за время её жизни кто-то успел
    занять то же время другой записью.

19. **Создание записи — одна функция (`createBookingCore` в
    `server/src/bookings.js`) на все три роли**, а не три похожих куска
    кода со своим `INSERT INTO bookings`. Клиент (`createBooking`),
    мастер (`masterCreateBooking`) и администратор (`adminCreateBooking`)
    — тонкие обёртки, которые различаются только тем, откуда берут
    `clientId`/`masterId` (из сессии или из тела запроса) и какие
    необязательные возможности разрешают (`holdId` — только клиенту,
    `overrideOverlap` — только админу), но сам INSERT, транзакция
    `BEGIN IMMEDIATE`, проверка слота и перехват ошибки триггера — общий
    код, который не может незаметно разойтись между ролями. Второго пути
    вставки записи в БД в коде приложения нет (`seed.js` — отдельный
    dev-скрипт для фикстур, не часть работающего API). Перенос
    (`rescheduleBooking`) и оба варианта отмены/смены статуса
    (`cancelBooking` для клиента, `adminSetBookingStatus` для админа)
    по той же причине сведены к одному внутреннему `writeBookingStatus()`
    для самой записи UPDATE — раньше это были два одинаковых по смыслу,
    но текстуально отдельных `UPDATE bookings SET status=...`.

20. **У `masters` нет отдельной таблицы-справочника ролей/учёток — `email`
    и `password_hash` добавлены прямо в `masters`**, как раньше в
    `clients`. Альтернатива — общая таблица `accounts`
    (`actor_type`, `actor_id`, `email`, `password_hash`), из которой
    `clients`/`masters`/`admin_users` ссылались бы на неё. Не стал:
    аутентификационных полей всего два, они уже устроены одинаково в
    `clients` и `admin_users`, а третья похожая таблица ради общности
    добавила бы join там, где раньше было прямое чтение строки, не решая
    при этом ничего нового.
