# Карта клиентских экранов

Источники: `prototypes/booking-prototype/Booking Prototype.dc.html` (лендинг,
запись, подтверждение), `prototypes/booking-prototype/Client Account Prototype.dc.html`
(личный кабинет, профиль, уведомления, служебные страницы),
`prototypes/booking-prototype/Booking Flow Diagram.dc.html` (схема связи
экранов, лежит рядом с прототипом, не в `docs/`), код API в `server/src/routes/`.

**Важно до чтения таблицы:** оба прототипа — полностью статические макеты. Ни
один экран в них сейчас не вызывает реальный API (`fetch` встречается только
внутри служебного `support.js` самого инструмента прототипирования, к `/api/*`
обращений нет). Все данные захардкожены прямо в коде экрана. Колонки
«эндпоинты» ниже — это то, чем экран **должен** питаться при вёрстке, а не то,
чем он питается сейчас.

Из экранов, которые вы просили — лендинг, авторизация, запись, личный
кабинет, профиль, уведомления, служебные страницы — в прототипах теперь есть
**шесть из семи**: лендинг, запись, подтверждение, личный кабинет, профиль,
уведомления, служебные страницы. Не хватает только экрана **авторизации**
(вход/регистрация) — он по-прежнему нигде не сделан, подробности в разделе
ниже. Экраны мастера/администратора («Админка») в файле есть, но в карту не
включены — по вашей просьбе.

## Экраны

| Экран | Файл прототипа | Что видит клиент | Эндпоинты данных | Эндпоинты кнопок | Переходы |
|---|---|---|---|---|---|
| **Лендинг** | `Booking Prototype.dc.html` (блок `isLanding`) | Хедер с именем мастера и кнопкой «Записаться»; хиро-блок с заголовком и CTA; сетка карточек услуг (название, описание, длительность, цена); футер | `GET /api/services` — список услуг для карточек. Мастер захардкожен («Кабанов Олег»), в реальном API мастеров может быть несколько — `GET /api/masters` сейчас нигде не используется | Кнопка «Записаться» (хедер) и «Записаться на консультацию →» (хиро) — переход на экран «Запись», без вызова API. Кнопка «Записаться →» на карточке услуги — переход на «Запись» с предвыбранной услугой, без вызова API. Ссылка «Смотреть услуги» — якорный скролл, без API | → Запись (любая кнопка «Записаться»). → Админка через ссылку в футере (не в карте, экран мастера/админа) |
| **Запись** | `Booking Prototype.dc.html` (блок `isBooking`) | 4 шага одной формой: выбор услуги, выбор даты (сетка на 7 дней вперёд), выбор времени (фиксированный список слотов), поля контактов (имя, телефон/email, комментарий); сайдбар с резюме записи | Услуги — `GET /api/services`. Даты в прототипе сгенерированы на клиенте (просто «сегодня + 7 дней»), в реальности часть дат может быть недоступна (выходной мастера/блокировка) — эту информацию сейчас неоткуда взять на этапе выбора даты. Время в прототипе — фиксированный список `['10:00','11:30','13:00','14:30','16:00','17:30']` для любой даты; реальный источник свободного времени — `GET /api/masters/:masterId/availability?date=...&serviceIds=...`, который надо вызывать заново при каждой смене даты/услуги и который учитывает уже занятые слоты | Кнопка «Подтвердить запись» должна вызывать `POST /api/bookings` (масter Id, serviceIds, startsAt, опционально holdId, comment) — в прототипе она просто пишет объект в локальный state, реального вызова нет. Ссылка «← На главную» — переход, без API | → Лендинг («← На главную»). → Подтверждение (после «Подтвердить запись») |
| **Подтверждение** | `Booking Prototype.dc.html` (блок `isConfirmation`) | Галочка-иконка, номер записи, статус («ожидает подтверждения» и т.п.), карточка с деталями записи (услуга, дата, время, имя, контакт, статус) | Данные берутся из ответа `POST /api/bookings` (в проде) — отдельного GET для этого экрана не нужно, если открывать его сразу после успешного создания. Если экран может открываться по прямой ссылке/обновлению страницы — тогда нужен `GET /api/bookings/:id` | Кнопка «На главную» — переход на Лендинг, без API. Кнопка «Открыть панель администратора» — переход на Админку (не в карте) | → Лендинг. → Админка (не в карте) |
| **Личный кабинет** | `Client Account Prototype.dc.html` (блок `isCabinet`) | Список записей клиента с вкладками «Предстоящие / Прошедшие / Отменённые», карточка на каждую запись (услуга, дата, время, код, статус), у предстоящих — инлайн-переброс на новую дату/время и отмена; отдельное пустое состояние на каждую вкладку | `GET /api/bookings` — возвращает все записи клиента одним списком, без параметра фильтра по статусу/периоду. Деление на «предстоящие/прошедшие/отменённые» для вкладок нужно делать на клиенте (сравнивать `startsAt` с текущим временем и смотреть `status`) — эндпоинт для этого не нужен, но и не делает работу за фронтенд | «Новая запись» — переход на Лендинг/Запись, без API. Вкладки-фильтры — переключение на клиенте, без API. «Перенести» → «Сохранить перенос» должен вызывать `POST /api/bookings/:id/reschedule` (startsAt) — в прототипе меняет только локальный state, реального вызова нет. «Отменить» должен вызывать `POST /api/bookings/:id/cancel` — тоже пока только локальный state | → Лендинг/Запись («Новая запись», «Выйти»). ↔ Профиль, ↔ Уведомления (общая навигация). → Служебные страницы (ссылка в шапке, только для предпросмотра состояний) |
| **Профиль** | `Client Account Prototype.dc.html` (блок `isProfile`) | Карточка с именем, email (нередактируемый, подписан «используется для входа») и контактом; кнопки «Редактировать» / «Сохранить» / «Отмена»; подтверждение «Изменения сохранены» | Прямого источника нет. Данные клиента в реальном приложении есть только в ответе `POST /api/auth/login` / `POST /api/auth/register` (`client: {id, name, email, contact}`) — их нужно держать в состоянии сессии на фронте, отдельного `GET /api/clients/me` в API нет | Кнопка «Сохранить» должна вызывать `PATCH /api/clients/me` — такого эндпоинта в API нет вообще (см. список ниже), поэтому в прототипе сохранение полностью локальное, ничего не персистится | ↔ Кабинет, ↔ Уведомления (общая навигация). → Лендинг («Выйти») |
| **Уведомления** | `Client Account Prototype.dc.html` (блок `isNotifications`) | Список уведомлений (точка-индикатор непрочитанного, заголовок, текст, время), бейдж с числом непрочитанных на вкладке в шапке, кнопка «Отметить всё прочитанным», переключатель «показать пустое состояние» для предпросмотра | Источника нет вообще — в API нет ни одного эндпоинта под уведомления клиента (ни списка, ни статуса прочтения). Весь список в прототипе — полностью придуманный мок | Клик по уведомлению и «Отметить всё прочитанным» должны вызывать эндпоинты пометки прочитанным — их не существует, сейчас всё меняется только в локальном state. Переключатель пустого состояния — служебный, только для прототипа, в реальном UI его не будет | ↔ Кабинет, ↔ Профиль (общая навигация) |
| **Служебные страницы** | `Client Account Prototype.dc.html` (блок `isService`, 4 подсостояния через `serviceKind`) | Один экран с переключателем сверху («Загрузка» / «Пусто» / «404» / «Ошибка») — для предпросмотра всех четырёх состояний без открытия разных файлов: спиннер с текстом загрузки; пустое состояние с CTA «Записаться на консультацию»; 404 с CTA «На главную»; общая ошибка с «Обновить» и «На главную» | Эндпоинта у этого экрана как такового нет — это набор состояний, в которые попадает **любой** другой экран, пока его собственный запрос выполняется, вернул пустой список или упал с ошибкой. Переключатель вкладок вверху — инструмент для ревью прототипа, не часть реального UI | «Обновить» на состоянии «Ошибка» должен повторно вызывать тот запрос, который упал (в прототипе просто возвращает экран в состояние «Загрузка»). «На главную» — переход на Лендинг, без API | Не самостоятельный переход — экран подставляется вместо любого другого, пока у него нет данных или что-то пошло не так |

## Что из списка экранов всё ещё отсутствует

- **Авторизация (вход/регистрация).** Ни в одном из двух прототипов формы логина/регистрации нет — форма записи на шаге «Контакты» просто спрашивает имя и телефон/email без создания аккаунта, а личный кабинет/профиль/уведомления открываются сразу, без экрана входа перед ними. Но реальный API требует авторизованного клиента (`Authorization: Bearer <token>`) для создания записи, просмотра, переноса, отмены и для всего личного кабинета — `POST /api/auth/register`, `POST /api/auth/login`, `POST /api/auth/logout` готовы и по-прежнему ничем не покрыты.

## Экраны, для которых в API не хватает данных — решения

Правило: бэкенд не трогаем, ищем решение на стороне экрана.

| Находка | Решение | Почему |
|---|---|---|
| Запись, шаг «Дата» — не видно, какие дни вообще доступны у мастера, до выбора конкретной даты | Можно собрать из существующих эндпоинтов | Дёргаем `GET /api/masters/:masterId/availability` по каждой из 7 видимых дат заранее и просто прячем/затемняем те, где список слотов пуст — отдельный «эндпоинт на неделю вперёд» не нужен |
| Запись, шаг «Время» — мастер нигде не выбирается, а `masterId` обязателен для доступности, удержания и создания записи | Данные в API на самом деле есть — `GET /api/masters` | Проблема не в нехватке данных, а в отсутствующем шаге на экране: пока мастер один — брать его `id` из этого списка автоматически, без отдельного элемента выбора |
| Личный кабинет — не видно статус удержания слота (`slot_holds`), если клиент не успел закончить запись | Убрать элемент из вёрстки | У API нет эндпоинта, который отдавал бы клиенту список его удержаний, а сами удержания живут 10 минут — это не тот объект, который стоит показывать как «черновик» в кабинете |
| Профиль — нечем ни получить, ни сохранить данные клиента | Данные для показа на самом деле есть — ответ `login`/`register` | Имя, email и контакт уже приходят при входе — их достаточно один раз сохранить в состоянии сессии на фронте и брать оттуда для показа; **сохранение изменений** так не решается (см. список ниже) |
| Уведомления — в API нет ни списка, ни статуса прочтения | Можно собрать из существующих эндпоинтов | При каждом открытии кабинета сравниваем статусы из `GET /api/bookings` со снимком, сохранённым в `localStorage`, и показываем изменившиеся записи как уведомления — работает только в одном браузере, без синхронизации между устройствами и без настоящей истории |

## Эндпоинты, которым не нашлось экрана — решения

| Находка | Решение | Почему |
|---|---|---|
| `POST /api/auth/register`, `POST /api/auth/login`, `POST /api/auth/logout` | Экран будем верстать позже | Это самостоятельный экран (вход/регистрация), а не кнопка или окно поверх другого экрана — под него нужна отдельная вёрстка, которой сейчас нет ни в одном прототипе |
| `POST /api/holds`, `DELETE /api/holds/:id` | Оставить как есть | Двойная запись на один слот и так надёжно исключена на уровне базы (транзакция + триггер — проверено вживую в разделе про конфликт слотов), поэтому удержание — это только UX-приятность, а не необходимость; подключать его — это ещё одно состояние экрана (создать при выборе времени, снять при уходе назад, учесть, что 10 минут может не хватить), которое пока не даёт прироста в надёжности |
| `GET /api/masters` | Добавить элемент на существующий экран | Как только мастеров станет больше одного — на экране «Запись» нужен явный выбор мастера, который наполняется этим эндпоинтом; пока мастер один, элемент не нужен — значение просто берётся из ответа автоматически (см. решение выше) |

## Что нельзя решить на стороне экрана

- Сохранение изменений профиля (имя, контакт) — нет эндпоинта, который принимал бы такую запись.
- Смена email (логина) клиента.
- Уведомления как полноценная функция — единый список на всех устройствах, история, создание при смене статуса записи на сервере.
